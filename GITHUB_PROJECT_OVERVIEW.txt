============================================================
1. PROJECT OVERVIEW
============================================================

Khata Ledger is a full-stack digital ledger application
designed to help shop/business owners maintain customer credit,
payments, balances, and transaction history digitally.

The application replaces traditional manual khata/ledger
management with a centralized digital system.

The project consists of two major applications:

1. Backend
   - REST API
   - Authentication
   - Customer management
   - Ledger management
   - Transaction management
   - Notifications
   - Reporting
   - Data export
   - Audit logging

2. Flutter App
   - Owner-facing mobile application
   - Customer-facing functionality
   - Dashboard
   - Customer management
   - Ledger operations
   - Transaction history
   - Reports
   - Notifications


============================================================
2. PROJECT GOALS
============================================================

Primary goals of the project:

- Digitize traditional customer khata management.
- Maintain customer outstanding balances.
- Record credit and payment transactions.
- Provide customers with visibility into their ledger.
- Notify customers when ledger activity occurs.
- Provide owners with reports and analytics.
- Support export of outstanding customer reports.
- Maintain reliable and auditable ledger operations.
- Prevent duplicate transaction processing.
- Keep the application scalable as transaction volume grows.
- Follow clean separation between application layers.
- Build the system with production-oriented practices.

------------------------------------------------------------

The ledger is the core business functionality of the application.

Supported ledger operations include:

- Adding due
- Recording payment
- Reducing due
- Maintaining current outstanding balance
- Recording transaction history
- Tracking balance after each transaction


The current balance is maintained separately from historical

------------------------------------------------------------

Transactions contain information such as:

- Owner reference

Transaction types are controlled using predefined application

5.6 IDEMPOTENCY
------------------------------------------------------------

The backend supports request-level idempotency for ledger
mutations.

A request identifier can be used to prevent accidental duplicate
processing when the same operation is submitted more than once.

This is particularly useful for:

- Network retries
- Client retries
- Duplicate requests
- Unstable connections


============================================================
6. LEDGER CONSISTENCY
============================================================

Ledger mutations are designed to keep the customer's current
balance and transaction record consistent.

A typical ledger mutation follows this conceptual flow:

1. Authenticate the owner.
2. Verify that the customer belongs to the owner.
3. Validate the requested operation.
4. Check for an existing idempotent request.
5. Calculate/update the customer's current due.
6. Create the corresponding transaction.
7. Record an audit entry.
8. Create the relevant notification.
9. Deliver the notification after the ledger operation.


Where supported by the database environment, database transaction
mechanisms are used to group related operations.

The application also contains fallback behavior for environments
where MongoDB transaction support is unavailable.


============================================================
7. CURRENT DUE VS TRANSACTION HISTORY
============================================================

The Customer record maintains the current outstanding balance.

The Transaction collection maintains historical ledger events.

Conceptually:

Customer.currentDue
    |
    +---- Current outstanding amount
    |
    +---- Used for fast balance access


Transaction
    |
    +---- Historical ledger event
    +---- Amount
    +---- Transaction type
    +---- Balance after transaction
    +---- Timestamp


This separation allows the application to retrieve the current
balance efficiently without calculating the entire transaction
history every time.

11. OUTSTANDING REPORT

Search input is handled as literal search text rather than allowing

============================================================
12. DATA EXPORT
============================================================

Outstanding customer reports can be exported into multiple formats.

Supported formats include:

- CSV
- Excel
- PDF


Export processing is designed to avoid loading the complete result
set into memory at once.

The backend processes export data in batches.

Current export behavior intentionally limits the number of
outstanding records processed by an export request.

Current configured maximum:

10,000 records


Current batch size:

500 records


This limit is intentional and may be revised later if business
requirements change.


============================================================
13. EXPORT PERFORMANCE
============================================================

Large exports are processed incrementally.

The backend uses batch-based retrieval instead of attempting to
load all matching records into application memory simultaneously.

This approach helps reduce:

- Memory usage
- Large response buffering
- Application-level memory pressure


CSV exports are streamed.

Excel exports use a streaming workbook writer.

PDF generation processes records progressively.

16. SEARCH SECURITY
============================================================

Search functionality must not directly interpret arbitrary user
input as a regular expression.

operations.

This prevents unintended regex behavior and reduces the risk of
regex-based query abuse.

22. DATA RETENTION STRATEGY
============================================================

The project is being designed with long-term data growth in mind.

Transaction data is expected to grow continuously as businesses
record ledger activity.

The current planned retention policy is:

- Keep recent transaction history in the primary database.
- Archive older transaction history.
- Preserve current customer balance independently.
- Avoid deleting historical financial information without an
  appropriate archive strategy.


Current agreed retention concept:

Recent transaction history:
90 days


Transactions older than the retention cutoff:
Eligible for archival


The retention cutoff is based on:

Current time - exactly 90 days


The archive system is a planned scalability feature and should be
implemented carefully so that archiving historical transactions
does not alter the customer's currentDue.


============================================================
23. PLANNED ARCHIVE SYSTEM
============================================================

The planned archive lifecycle is conceptually:

ACTIVE
   |
   | transaction reaches retention cutoff
   v
ELIGIBLE_FOR_ARCHIVE
   |
   | archive job
   v
ARCHIVED
   |
   | optional verification
   v
REMOVED_FROM_PRIMARY_DATABASE


The archive mechanism should ensure:

- No change to currentDue
- No accidental deletion of active transactions
- No loss of historical records
- Owner/customer relationships remain recoverable
- Archived records remain identifiable
- Archive operations are idempotent
- Failed archive operations can be retried safely


The archive storage implementation is intentionally not specified
in this public document.

The archive architecture may eventually separate:

MongoDB


Historical/archive data:
Object storage or another dedicated archival system

============================================================
32. DATA INTEGRITY PRINCIPLES
============================================================

The following principles are important for the ledger:

1. currentDue must represent the current outstanding balance.
2. Ledger mutations must be validated.
3. Payment/reduction must not exceed the applicable due.
4. Transactions must record the resulting balance.
5. Duplicate requests must not create duplicate ledger mutations.
6. Historical transaction data must not be silently modified.
7. Archive operations must not modify currentDue.
8. Owner/customer isolation must always be enforced.
9. Deleted users must be handled consistently.
10. Financial records should not be physically deleted casually.


============================================================
33. OWNER DATA ISOLATION
============================================================

Owner-specific data must remain isolated.

A request belonging to one owner must not be able to access or
modify another owner's customers or transactions.

Ownership checks must be performed on the backend.

Client-side checks alone are NOT considered sufficient security.
