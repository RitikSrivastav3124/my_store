Performance investigation report - Flutter app freeze (main-isolate work & rebuilds)

Instructions: this file lists only confirmed runtime causes of unnecessary rebuilds, repeated API calls, or main-isolate work. Each entry contains: File, Line, Why it rebuilds / triggers work, Confidence.

1) File: App/lib/presentation/viewmodels/base_view_model.dart
   Lines: 14, 20, 31
   Why: `guard()` sets `_loading = true` and calls `notifyListeners()` before the awaited action, and calls `notifyListeners()` again in `finally` after the action completes. Any widget listening to a ViewModel using `BaseViewModel` (e.g., `OwnerViewModel`, `NotificationViewModel`, `CustomerViewModel`) will receive two notifications per network call (start + end), causing UI rebuilds of consumers/selectors that depend on those ViewModels. This doubles rebuilds for each request and causes extra main-isolate work for large lists/charts.
   Confidence: High

2) File: App/lib/presentation/viewmodels/auth_view_model.dart
   Lines: 21 (bootstrap start), 30, 39, 55, 63 (notifyListeners calls)
   Why: `bootstrap()` is invoked during provider creation in `main.dart` (see entry below) and does `notifyListeners()` in `finally`. That `notifyListeners()` forces `RoleGate` (which uses `context.watch<AuthViewModel>()`) to rebuild and may mount the appropriate shell screen (owner/customer). Mounting those screens runs their `initState` callbacks which perform network calls (see owner/customer shells). Other `notifyListeners()` calls on login/register/logout will also rebuild listeners. These are real triggers for subtree rebuilds and for the initial sequence of API calls that follow mount.
   Confidence: High

3) File: App/lib/main.dart

   Why: All `ChangeNotifierProvider` instances are created at app root here. `AuthViewModel` is created with a cascade-call to `..bootstrap()`. The bootstrap async call (and its `notifyListeners`) runs during provider initialization and leads to `RoleGate` rebuild and the subsequent mounting of shell screens which perform network requests (`refreshDashboard`, `loadCustomers`, `refresh`). Providers are not created elsewhere in the app, so provider re-creation is not the cause of repeated calls.

Notes / Root cause summary (verified):
- The single most actionable cause of extra main-isolate work is the pair of `notifyListeners()` calls inside `BaseViewModel.guard()` (start + end). Every network call from view models causes two notifications; any `Selector` or `Consumer` that rebuilds a large tree (lists, charts) will rebuild twice per request. That is a confirmed source of doubled rebuilds and is the most likely contributor to the observed freezes when many requests and large widgets are present.

- Secondary contributors are the app startup flows: `AuthViewModel.bootstrap()` (called during provider creation in `main.dart`) which causes the top-level `RoleGate` to rebuild and mount the appropriate shell, and the shell `initState` callbacks that immediately call several network methods (`refreshDashboard`, `loadCustomers`, etc.) on mount. These combine to create a burst of network operations at startup.

What I did NOT find (confirmed negatives):
- No provider instances are created inside frequently rebuilt widgets.
- No FutureBuilder or Timer-based polling loops that would periodically call APIs.
- No TextField keyboard-focused rebuild loop.
- No obvious infinite notify->build->notify cycles in `build()` code.

Backend Security and Risk Audit - Problems

Scope: Read-only audit of c:\Flutter projects\my_store\backend. No secrets are recorded.

HIGH - Ledger balance updates are unsafe when MongoDB transactions are unavailable.
Location: backend/src/services/ledger.service.js, runWithOptionalTransaction and LedgerService.mutateDue; backend/src/repositories/customer.repository.js, updateById.
Problem: The service reads currentDue, calculates nextDue, then updates the customer in a separate operation. The transaction helper retries without a session when transactions are unsupported.
Scenario/impact: Concurrent payments or due additions can read the same balance and overwrite one another. Transaction records and balanceAfter values can disagree with the customer balance.
Confidence: Confirmed.
Recommendation: Require a replica set or use an atomic conditional update/optimistic concurrency check. Add concurrent ledger tests.
Priority: P0.

HIGH - Firebase push notifications can be sent before a ledger transaction commits.
Location: backend/src/services/ledger.service.js, LedgerService.mutateDue; backend/src/services/notification.service.js, createAndPush.
Problem: FCM is called while the database transaction is still open.
Scenario/impact: A later database failure can roll back the ledger while the customer has already received a notification for the rolled-back change.
Confidence: Confirmed.
Recommendation: Commit database changes first, then dispatch via an outbox or queue with retry and idempotency handling.
Priority: P1.

MEDIUM - Refresh-token rotation is race-prone.
Location: backend/src/services/auth.service.js, AuthService.refresh; backend/src/repositories/refreshToken.repository.js, findActiveByHash and revoke.
Problem: The old token is read, a replacement is created, and revocation happens afterward. The revoke result is not checked.
Scenario/impact: Two simultaneous refresh requests can both use one refresh token and create valid replacement sessions.
Confidence: Confirmed.
Recommendation: Atomically claim/revoke the old token and create its replacement in one transaction. Reject when the revoke affects no document.
Priority: P1.

MEDIUM - Public owner registration is enabled.
Location: backend/src/routes/auth.routes.js, POST /register; backend/src/services/auth.service.js, registerOwner.
Problem: Any unauthenticated caller can create an active owner account.
Scenario/impact: Unauthorized users can provision owner tenants and use all owner customer and report APIs for those tenants.
Confidence: Confirmed; intended product policy needs verification.
Recommendation: Disable public registration after bootstrap or require an invitation/admin provisioning workflow.
Priority: P1.

MEDIUM - Search input is compiled as an unescaped regular expression.
Location: backend/src/repositories/customer.repository.js, listForOwner; backend/src/services/report.service.js, outstanding.
Problem: User-controlled search text is passed to new RegExp without escaping metacharacters.
Scenario/impact: Regex-heavy input can cause expensive database matching and CPU pressure.
Confidence: Confirmed.
Recommendation: Escape input for literal matching, use indexed search, and apply query timeouts.
Priority: P1.

MEDIUM - Report exports perform expensive in-memory work.
Location: backend/src/services/export.service.js, outstandingCsv, outstandingExcel, and outstandingPdf.
Problem: Each export requests up to 10,000 records and builds CSV, Excel, or PDF buffers in memory.
Scenario/impact: Repeated large exports can consume substantial CPU and memory and destabilize the Node process.
Confidence: Confirmed.
Recommendation: Stream or queue exports, enforce a lower maximum, and apply export-specific throttling.
Priority: P1.

MEDIUM - Rate limiting is process-local.
Location: backend/src/middleware/rateLimiter.middleware.js, apiRateLimiter and authRateLimiter.
Problem: The default in-memory store is used.
Scenario/impact: In a multi-instance deployment, requests distributed across instances bypass the intended aggregate login/API limits.
Confidence: Confirmed for multi-instance deployments.
Recommendation: Configure a shared Redis-compatible store and verify proxy/IP configuration.
Priority: P1.

LOW - FCM tokens are unnecessarily exposed and unbounded.
Location: backend/src/models/user.model.js, fcmTokens; backend/src/controllers/auth.controller.js, registerFcmToken.
Problem: User responses can include fcmTokens, and the token array has no count limit.
Scenario/impact: Device registration identifiers are exposed and repeated registrations can grow user documents.
Confidence: Confirmed.
Recommendation: Exclude fcmTokens from public responses, cap the array, and prune stale tokens.
Priority: P2.

LOW - Customer creation may duplicate password hashes in audit data.
Location: backend/src/services/customer.service.js, create; backend/src/services/audit.service.js, record.
Problem: The complete created user document is passed into audit newValue. The document may still contain its password hash despite select:false affecting normal queries.
Scenario/impact: A database reader could find password hashes duplicated in audit records, increasing offline-cracking exposure.
Confidence: Likely; verify by inspecting a sanitized audit record.
Recommendation: Store an explicit allowlist of audit fields and never persist authentication material.
Priority: P1.

LOW - Upload middleware is inactive and insufficient for future uploads.
Location: backend/src/middleware/upload.middleware.js, multer configuration.
Problem: No route currently uses it. If enabled, it trusts the client MIME type and checks no file content signature.
Scenario/impact: A forged image MIME type could allow malicious content to be accepted.
Confidence: Confirmed inactive; future risk.
Recommendation: Remove unused upload support or add content validation, extension policy, authorization, and isolated storage before use.
Priority: P2.

BUSINESS LOGIC RISK - Credit limit is stored but not enforced.
Location: backend/src/services/ledger.service.js, LedgerService.mutateDue.
Problem: addDue never checks customer.creditLimit.
Scenario/impact: If creditLimit is intended as a hard limit, an owner can record debt above it.
Confidence: Needs verification because the intended meaning of creditLimit is not documented in the implementation.
Recommendation: Define the policy explicitly and enforce it atomically if it is a hard limit.
Priority: P1 if confirmed.

- JWT_REFRESH_SECRET is configured but unused because refresh tokens are opaque random values: backend/src/config/env.js and backend/src/utils/jwt.js.
- Swagger and health endpoints are publicly accessible: backend/src/app.js and backend/src/routes/index.js. Confirm this is acceptable in production.
- No Dockerfile, Render manifest, Procfile, or equivalent deployment manifest was found in backend.
- npm audit --omit=dev reported six dependency advisories involving body-parser, brace-expansion, fast-uri, fast-xml-parser, js-yaml, and protobufjs. Dependencies were not upgraded.
- ESLint could not run because ESLint 9 requires an eslint.config.js/mjs/cjs file, which is absent. JavaScript syntax checks passed.
- Existing tests passed: 2 suites and 3 tests. They do not cover cross-owner access, role isolation, refresh races, concurrent ledger writes, exports, Firebase failure, or credit-limit behavior.

Overall verdict: NOT READY FOR PRODUCTION until the ledger concurrency, transaction/notification ordering, token rotation, registration policy, and production configuration issues are addressed.
